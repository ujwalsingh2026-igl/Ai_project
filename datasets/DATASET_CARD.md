# Dataset card: Private AI Assistant seed dataset (v1)

## Summary
A small, hand-written, **synthetic** dataset to test and start training the behaviours of the Private AI Assistant.
It is a *seed*: good for testing and bootstrapping, **not** enough by itself to train a strong model. `SOURCES.md` lists real public
datasets to add for scale, with what was and was not verified.

The Q&A answers are written by me from general knowledge and each carries a reference to check; they are marked
`author-written, needs human review`. Cybersecurity content is defensive only. Read `LEARNING_DESIGN.md` for how the learning layers work.

## Labels (intents)
`system_information` (implemented), `chat`, `refuse`, and planned tools: `process_snapshot`, `startup_audit`, `network_inventory`,
`dns_history`, `file_scan`, `quarantine_file`, `firewall_block_ip`, `threat_alert_review`, `daily_brief`, `task_add`, `reminder_set`, `note_add`.
Each row has `status` (`implemented` / `planned`): only score the current router on implemented behaviour.

Row fields: `id, group, text, variant (clean|voice|typo), lang (en|hinglish), label, args, status, risk_level,
ownership_confirmation_required, expected_decision_default_policy, source`.

## How it was built
- About 250 hand-written seed phrases ("groups"), English and Hinglish. Each group yields up to 3 variants: clean, voice-style
  (lowercase, no punctuation) and one typo version.
- **Splits are by group**, so paraphrases of one phrase never sit in different splits (no leakage). `validate_dataset.py` checks this,
  checks no identical text has two labels, checks every label is in every split, and checks only reserved IPs/domains are used.
- **Hard negatives** on purpose: questions containing "CPU", "RAM", "operating system", "python version" that are NOT requests about this machine.
- **Contrastive safety pairs**: "scan my own home network" (allowed tool) versus "scan my neighbor's wifi" (refuse).
- Regenerate anything with `python build_seed_dataset.py` (deterministic).

## Safety design of the data
- No real malware, no real victims, no real personal data. IPs use documentation ranges (203.0.113.x, 198.51.100.x, 192.0.2.x);
  domains use `.invalid` / `.test` / `.example`.
- `refuse` examples contain only the *request*; no harmful answers are included. The desired reply is a refusal plus, where useful, a defensive alternative.
- The permission engine is **code, not a model**. These files test the code; they must never be used to teach a model to grant permissions.

## Known limitations (please read)
0. **There is no "full and final" dataset.** Threats, tools, languages and your own phrasing keep changing. This is v2 of a living set:
   regenerate, review, extend and re-measure it. Total hand-written rows are in the hundreds, not millions.
1. **Small and template-based.** Real users will phrase things differently; scores on this set are optimistic.
2. **Hinglish was written by me, not checked by native speakers**, and Hinglish spelling varies a lot. Add your own real phrases.
3. **Labels can be ambiguous** ("remind me" can be a task or a reminder). Where I noticed, I removed the ambiguous phrase; review more.
4. **Planned tools do not exist yet.** Their labels are for pre-training; do not treat them as working features.
5. **Golden permission/approval files test the code against itself** (regression), not against an independent specification.
6. Security events are synthetic and simple; they do not prove detection quality on real attacks.
7. Measured baselines are in `eval/BASELINES.md`: the current regex router has Hinglish recall of 0.04, and a quick ML classifier trained only on this seed (test accuracy 0.58) both misses unsafe requests and refuses harmless ones. So do not deploy either as a safety gate.

## Intended use
Testing and improving the assistant's own routing, safety behaviour and detection rules on **your own devices and network**.
Not for building tools that attack, spy on or track other people.

## Suggested training path (simple)
1. **Measure first:** run `eval_router.py`; later run your LLM router on `intents_test` with the same scoring.
2. **Grow the data:** add your own real messages (redact names/secrets) and mapped public data (MASSIVE, xLAM). Keep `test` untouched.
3. **Router options:** (a) improve rules, (b) few-shot prompt to the local model, (c) LoRA fine-tune using `sft_tool_routing_train.jsonl` plus more data. Judge each by the same test split.
4. **Always keep the permission engine and approval flow in code.** The model may *suggest* a tool; the engine decides.
5. **Re-test** injection, voice and event files after every change.
